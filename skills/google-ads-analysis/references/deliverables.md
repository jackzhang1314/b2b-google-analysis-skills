# 小白看得懂的交付

默认一个可独立打开的 `report.html`，不用安装网页框架，不加载外部统计脚本。按问题需要附 `negative-review.csv`、`measurement-review.csv`、`evidence-index.json`。不为凑文件把每一步拆成一份文档。

默认读者不懂广告。主页面让他能回答“发生了什么、我该做什么、为什么、做完怎么看”，不是要求他先学会读报表。细节足够支撑操作，但不要把长篇教程塞进每一条建议。

HTML 顺序：

1. **一分钟读懂**：最多三个优先发现，用自然语言说明对生意的意义。标清日期、比较对象、币种以及报告是否已经执行任何改动；标题不用内部状态码或缩写。
2. **按顺序行动**：每项写出具体对象、操作步骤、负责角色、预期帮助、检查结果的方法与仍待确认的条件。缺证据时明确这一步是在查清问题，不承诺改变收益。
3. **看懂必要数字**：花费、点击、每次点击花费等指标附一句解释；首次出现“转化”就说明具体记录了什么，不能让用户误以为是客户或订单。小数来自归因分配时用日常例子解释，不把它四舍五入成客户数。
4. **按需看明细**：变化图表、字词分类和测量结论。长表、专业配置、证据编号与原始状态码折叠后置。表格上方写明如何使用；不要让用户靠横向滚动和猜字段才能找到下一步。
5. **方法及限制**：已核实与未核实、取数时间、来源和下载。保留缺失、回补、作用范围和不确定性；用户看主页面即可知道结论边界，技术证据可以另行展开。

## 每条优先建议必须能回答

| 内容 | 写法 |
|---|---|
| 发现了什么 | 具体对象和必要数字；事实与可能解释分开 |
| 为什么要管 | 影响获客判断、预算分配或排查效率的哪一环 |
| 谁来、怎么做 | 用角色称呼，如“负责广告的同事”“销售”；给可完成的步骤，不只说“优化目标”“检查漏斗” |
| 预期帮助 | “减少不相关咨询”“避免误停能带来询盘的词”；没有实验就不写节省金额或增幅承诺 |
| 做完看什么 | 记录执行时间、范围和真实业务结果；结合转化回补与可比窗口复盘，不套固定三天见效 |
| 什么情况先不做 | 业务范围不清、已有联系信号、规则待核验或证据不足时先补哪一项 |

示例：不用“核验主转化归因后优化目标”，改为“先请销售核对网站实际收到的咨询，区分真正询价、无关咨询和仍需跟进；再让负责广告的同事确认哪些提交被谷歌计入成绩。这样能避免把留过邮箱但没有采购需求的人都当成获客成功。未核实前，先不要因三天没有平台转化就停掉主营业务的词。”示例仅示范表达，实际判断须有本次证据。

## 术语与数字

- 搜索字词＝客户真正输入的搜索内容；关键词＝广告里设置的匹配条件。否定关键词＝限制某些搜索触发广告，不是删除网站内容。
- 精确否定解释为本次选定的较窄匹配方式；保留原文和所属系列，不让新手把完整词擅自拆成词根或扩大到账户。实际匹配规则另给官方来源。
- CPC先写“平均每次点击花费”；CTR先写“看到广告后点击的比例”。不用缩写当表头的唯一解释。
- 转化先说明动作，如“邮箱提交的记录”；“所有转化”还可能包括其他联系动作，不能与主转化相加当客户数。平台动作、独立联系人、合格询盘、报价和成交分开。
- “目标”解释为谷歌用来判断广告是否达成预期的动作；不要自动建议把更多动作改成主要目标让报表好看。
- 固定转化价值用“给一次行为设置的参考分值”解释。即使界面显示货币，也不是已经收到的钱；没有真实收入和成本，不算真实ROI。
- 非中文搜索词若影响用户审核，保留原文并加中文意思或意图解释。翻译不明确就注明，不能把猜测当业务排除依据。

## 从看懂到开始做

- 每项优先建议给一段可直接发给Codex的任务，支持复制并有成功提示；复制受限时展开文字供手动复制。提醒用户同时提供报告。默认任务是继续读取、整理和核对，不借“复制任务”自动执行广告改动。
- 第一步告诉用户从哪里开始、最少需要什么资料。例如核对询盘时，先看平时接收网站咨询的邮箱或已有表格，记录日期、需求、是否承接、能否联系、跟进结果和已核实来源。同一需求合并；未知填待确认，不先要求安装客户管理系统。收到日期与广告互动日期分开，没有来源证据不强行算广告有效询盘成本。
- “销售、网站、广告负责人”是角色，一个人兼任也可以。不要把报告写成必须有一整支团队才可操作。
- 区分当前取数能力与未来执行能力：只读MCP不能写入广告。报告给出拟改动对象、范围和理由；真要实施时，再检查用户对具体变更的授权及工具/后台的编辑权限。不能写成给一句同意就让只读连接获得写权限。
- 用后台原名加解释，不另造“主成绩”等模糊术语。“第二步”等字样如果是动作名称，明确它不是教程步骤，且名称本身不证明实际触发条件。

## 页面必须实际检查

交付前按新手读一遍主页面：是否能在不打开明细的情况下说出先做哪件事；步骤是否足以交给相应角色；术语是否已解释；是否把尚未实施的建议写成了已有收益。使用用户常用浏览器的Codex Computer Use打开最终交付路径，检查顶部、行动、主要明细和页尾；不能只验证生成脚本。

- 金额、百分比和次数不能断在两行；宽表保留横向滚动，长表限制阅读区域并保留表头。窄屏可改为带字段名的逐条卡片，不能只把整张宽表缩小。
- 搜索/筛选要显示结果数、清空入口和无结果说明；无结果不代表账户没有这类搜索。保留完整下载与实际覆盖范围，不能让筛选隐藏数据的事实变成业务结论。
- 实点复制、筛选、展开和下载。下载文字说明给谁、做什么，待审表不写成可直接批量导入。只下载本报告产物，不操作广告。
- 检查窄窗口或放大显示后，恢复用户原有显示。浏览器预览失败如实记录；静态/模拟DOM检查、桌面放大检查都不能冒充真实手机或真实小白试用。

证据索引每条包含 ID、资源与过滤、日期、粒度、行数、限制、文件与摘要 hash，不写凭据或完整敏感标识。账户数据留用户本地，不打进对外分发的 Skill 包。

业务背景只记录用户已确认的产品/地区/客户/排除项/竞品策略及更新时间；网站推测单列为待确认。用户不用学习 GAQL 或内部 JSON，Codex 负责生成这些输入。

可直接说：

- “帮我分析最近三个完整日，和上周同星期比，告诉我优先处理什么。”
- “检查搜索字词，列哪些可以考虑否定，哪些不要误伤，暂时不要修改账户。”
- “检查这些转化有没有把点击按钮当成询盘，转化价值能不能当收入。”
- “按上次报告复盘；先确认哪些建议真的执行过，再比较变化。”

HTML 必须转义所有外部文本，保留手机可读和打印基本版式；下载 CSV 避免公式注入。无证据不写“节省了多少钱”“ROI 提升多少”或“全账户已经检查完”。
