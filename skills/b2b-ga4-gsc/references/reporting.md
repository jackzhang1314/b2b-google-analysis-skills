# 让客户看懂，并知道下一步做什么

默认读者是不了解广告和数据的外贸企业负责人。保留分析依据，把理解成本留给 Codex。不要把工具输出、英文指标表或研究笔记直接当最终报告。

## 阅读顺序

1. **先给结论。** 用短段落回答网站目前主要发生了什么、对采购获客意味着什么、优先处理哪件事。前屏只放与问题相关的少量数字，标真实分析日期。
2. **再讲理由和行动。** 最多三项优先事项，写到具体页面、查询词或询盘环节。其余问题归入观察/后续，不制造长而无差别的待办。
3. **最后展开数据。** 需要时查看来源、比较期、筛选、样本和详细表格。重要缺证必须放在对应结论旁，不能藏在页尾免责声明；技术字段、证据 ID 和 API 参数可折叠。

深度随问题变化。只问首页，就重点解释首页；完整分析再覆盖 GA4 的来源/页面/路径和 GSC 的查询/页面/市场。不能为了“通俗”省掉必要核验，也不因模板要求编造缺失数据。

## 每个重点建议要回答的问题

用自然段或短步骤组合，按需要展开，不强制六个小标题反复出现：

- **发生了什么？** 用相同范围的绝对数和变化说明，不单独摆涨跌箭头。
- **为什么值得关注？** 把数据联系到客户的采购目标，分清已看到的事实、可能原因和待核验项。
- **具体怎么做？** 指明页面/查询/入口，给执行人能照做的 1–3 步；有条件就写先决条件。不能停在“优化 SEO”“提高转化率”。
- **预期帮助是什么？** 解释路径，例如“让采购商更快确认能否承接，再发起咨询”；没有实验或销售证据，不写保证增加多少询盘。
- **谁来做、怎样知道有效？** 区分老板、网站负责人、内容/SEO 人员和销售；说明改完后比较什么、何时复看，什么时候先停下。

## 语言与数字

先用中文说含义，再在必要时带术语。第一次出现就解释；避免一口气堆 CTR、CVR、UTM、session、attribution。后续可以使用已解释的简称。需要精确定位时保留原英文搜索词、URL、事件名。

| 指标/术语 | 面向客户的说法 |
|---|---|
| GSC 曝光 | 你的网站在 Google 搜索结果中被展示的次数，不等于人数 |
| CTR | 看到搜索结果后点进来的比例；例如每展示100次，有2次点击，就是2% |
| 平均位置 | 搜索结果中位置的平均值，数字越小越靠前；不是每个人实时看到的固定名次 |
| GA4 会话 | 一次网站访问；同一个人可以来多次 |
| 互动率 | 达到 GA4 互动条件的访问比例，可帮助观察使用情况，不能直接判断是否采购客户 |
| 关键事件 | 网站预先标记的重要动作，例如咨询按钮或表单动作；需核实它是否代表实际成功询盘 |
| 着陆页 | 访客进站时看到的第一个页面 |
| 归因未知 | 现有记录不能可靠判断这条询盘来自哪里 |

比率变化解释成百分点，必要时补“每100次”的例子。例如 5%→3% 是少2个百分点；若每期只有几次访问，先说明样本不足，不把该例子作为真实趋势。不同范围不能共用分母。

### 表达示例（虚构情境，只示范写法）

不要只写：“首页 CTR 下降，优化元数据。”

可以写：“这个采购词让首页展示了1,000次，只有10次点击，也就是每展示100次约有1次被点进。先检查这些展示来自哪些国家、搜索位置有没有变化，再核对标题是否清楚说明我们能提供的服务。建议网站负责人先改这一页的标题和开头介绍，保留品牌与有效主题。这样有望让匹配的采购商更快判断页面是否值得看；能否增加点击和询盘，需要观察相同查询及销售反馈。”

不能从低点击率直接推出“标题是唯一原因”，也不能将这个示例的数值复制到真实报告。

## 文件与复盘

交付独立 HTML，手机可读；行动清单列“优先做什么、为什么、具体步骤、预期帮助、负责人、怎样验收”。CSV 防 `= + - @` 公式注入。原始响应、日志和完整核验 JSON 放私有目录；客户版不放凭据、联系人、制作日期或内部试验记录。

脚本 actions 中：fact 写观察事实；hypothesis 解释可能原因、经营影响及缺证；action 写具体步骤和预期帮助；owner/verification/stop_rule 写责任和复盘。脚本不能判断这些中文结论是否正确，Codex 仍须逐项核对原始证据并补齐业务说明。

交付前按读者视角自查：只读结论能否知道先做什么？建议能否交给具体负责人？术语是否已解释？预期帮助是否被误写成保证？不知道的地方是否说明下一步核验？发现指标堆砌就重写相关段落，不额外给客户一份内部评分表。

下次先看哪些改动真正执行，再比较同范围。若同时改了流量、内容和表单，不能把结果只归给某一项；记录回退条件。不默认创建定时任务。
